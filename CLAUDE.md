# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Retrieval-augmented Q&A over public compliance documents (NIST AI RMF, EU AI Act, public 10-K filings) with a scored evaluation harness and dense retrieval. Building in public; target ship September 15, 2026. Ingestion, retrieval, generation, and the HTTP API are implemented under SPEC-003 through SPEC-006. SPEC-007's first job — deciding hybrid against dense-only — is **done** (2026-08-05, vector-only wins, p = 0.000488) and the branch is deleted; the harness itself, the frontend (SPEC-009), and deployment (SPEC-010) are not yet written.

## Commands

Everything runs through uv:

```bash
uv sync                          # install (CI uses --frozen)
uv run pytest                    # all tests
uv run pytest tests/test_scaffold.py::test_healthz   # single test
uv run ruff check . && uv run ruff format --check .  # lint
uv run pyright                   # type-check (strict on src/, basic on tests/)
docker compose up -d             # api on :8000 + pgvector Postgres on :5432
```

CI (`.github/workflows/ci.yml`) runs one job with sequential gates **lint → type-check → test**, with a pgvector service container and `DATABASE_URL=postgresql+asyncpg://rag:rag@localhost:5432/rag`. Run the same three commands in the same order locally before pushing. Pre-commit runs ruff only; pyright is deliberately CI-only.

pytest-asyncio is in `auto` mode — async tests need no marker.

## Spec-driven workflow (binding — from SPEC-000)

Specs in `/specs` precede all code. The process:

1. Specs are `specs/SPEC-NNN-name.md`, numbered sequentially, with **exactly six sections in order**: Purpose · Non-goals · Interface · Key decisions · Acceptance criteria · Test plan.
2. Acceptance criteria must be objectively testable — each names the command, assertion, or observable state that proves it.
3. Tests are written **from the acceptance criteria, before implementation**.
   - **After writing any test, verify it fails when the behavior under test is broken.** Break the behavior — invert a condition, delete the guard, add the consumer the code forbids — run the test, watch it fail, then restore. A test never observed failing asserts the author's intent, not the system's behavior. **Three tests in this project have passed while proving nothing:** the savepoint blind spot (the app's own sessions could not see the fixture's uncommitted rows), the verdict-prefix check, and a request-id test asserting against stub log records that were never emitted. A fourth was caught by this rule during SPEC-006's second review — the concurrency measurement read peak overlap, which timing made 2 even when three sessions were open. A fifth was SPEC-006 AC-7: it asserted the request id on `caplog` records, and `caplog` reads `LogRecord` objects before any formatter runs, so the test structurally could not observe that no formatter existed and the id reached no operator — it proved the half of KD-5 that worked and was blind to the half that did not. (Fixed in `424b667`; AC-7 now asserts on rendered output.) A sixth is SPEC-006 AC-12's "a scrape opens no database connection": it built an app with **no budget configured**, so the headroom snapshot — the only code on that path that could open one — never ran, and the zero it asserted was a statement about absence rather than about behavior. Proved by mutation: make the scrape query only when a budget is configured, and the old test passes while the corrected one fails. **That one was found and then filed as "true but untested", which is its own failure mode** — noticing the shape and reaching for the milder label. "Untested" means nobody checked; this was checked, and the check could not have failed. If a passing test's premise makes its subject unreachable, it belongs in this list, not in a softer one. A seventh was caught by this rule before shipping, during KD-16 amendment 5: the test proving `max_cost` is an **upper bound** on a query's cost ran against a four-chunk fixture, where the output term is so much larger than the input term that mutating the input bound into a plausible estimate (`len(prompt) // 4`) left the test green — the total still cleared the actual cost, for a reason that had nothing to do with the half being mutated. **A bound with two terms needs a fixture where each term dominates in turn**, or the test only ever exercises the larger one. The failure mode is uniform: the assertion was true for a reason unrelated to the behavior. Only the failing run distinguishes them, and **a test that inspects an intermediate object rather than the output is the shape to be most suspicious of** — closely followed by one whose fixture makes the quantity under test negligible.
   - **An eighth, and the meta-observation it forces** *(2026-08-02)*. The OR-fallback in SPEC-004 AC-12 amendment 5 has a test asserting that a *working* conjunction is left alone. It used the query `quarklebit` — **one term. A single-term OR is identical to a single-term AND**, so the assertion held for a reason unrelated to the behaviour, and a mutant that deleted the conjunction entirely and always fell back passed it. Caught by mutation, fixed with `quarklebit govern` (1 chunk under AND, 3 under OR). Same family as the earlier instances: the fixture made the quantity under test degenerate.
   - **A ninth, and the first introduced by an architecture change rather than by authorship** *(2026-08-05)*. SPEC-004 AC-6 asserted that hybrid beats vector-only at k = 1 on citation queries. It was correct when written, correctly went red when the OR fallback broke it, and was carried as a strict `xfail` with a named removal trigger. **The trigger fired — SPEC-007 KD-12 settled fusion by deleting the branch — and re-arming the assertion would have installed a test that cannot fail**, because the two arms are now identical by construction. The run confirms it: citation `recall@1` reads 0.857 in both columns.
   - **The distinction that makes it worth its own entry: every previous instance was created by how a test was written** — a degenerate fixture, an intermediate object, a single-term query. **This one would have been created by the system moving underneath a test whose text never changed.** Nobody would have edited it, no review would have seen a diff, and a strict `xfail` flipping to green reads as good news. **So the removal trigger on an `xfail` needs to name what to do, not just when**: AC-6's said "delete this marker rather than widening it", and the honest action turned out to be deleting the *assertion*. Retired, not re-armed.
   - **A tenth, and the first that could fail in one direction only** *(2026-08-07)*. SPEC-007 KD-13 amendment 1 added a paired-difference interval, and with it a **simulated coverage check**: 2000 replications at the observed table, asserting coverage ≥ 0.93. Mutating the correlation term's sign from `−2φ` to `+2φ` — the single most likely error in the formula — **left the coverage test green.** A wrong-signed correlation makes the interval **wider**, a wider interval **over-covers**, and a coverage floor is satisfied by over-coverage. The mutation was caught only by a separate assertion that pairing must *narrow* the interval relative to the independence construction.
     - **The generalisation, which is the reason this is worth an entry: a test asserting that a bound holds is blind to any change that loosens it.** Coverage floors, "at most" assertions, timeouts, spend ceilings, `assert latency < X`, `assert cost <= Y` — every one of them passes when the quantity moves in the safe direction, and moving in the safe direction is not the same as being right. A test that says *"the interval covers at least 95%"* cannot tell a correct interval from one twice as wide; a test that says *"the request finished under 2s"* cannot tell a fast path from a cache that silently returns the wrong answer instantly.
     - **What separates this from the nine above: those were tests that could not fail. This is a test that could not fail in one direction**, which is why no amount of *reading* it would have exposed it — the assertion is well-formed, the fixture is the real table, the threshold is justified, and nothing about the code is suspicious. **Only the mutation distinguishes them**, and only a mutation chosen in the loosening direction. The rule 3 discipline — break the behaviour, watch it fail — has to include *which way* to break it: for a bound, break it **outward**, because inward is the half the assertion already covers.
     - **So a one-sided assertion needs a second assertion on the other side, or a stated reason there is nothing to check there.** Here it is a two-sided coverage window plus the narrowing property; the honest general form is that a bound and a tightness claim are two assertions and a spec that makes both should test both.
   - **The meta-observation, which is the part worth keeping: reaching for the milder label is part of the failure mode.** AC-12 was first filed as *"true but untested"* and had to be re-filed as a passing test that could not fail. This one was described accurately — a mutant survived because OR and AND coincide at one term — and then filed as *"worth flagging."* **The shape is easier to see than it is to admit is the shape.** When a passing test's premise makes its subject unreachable, it belongs in this list under its own name; "untested", "worth flagging", "a nuance", and "an edge case" are all the same evasion, and noticing the defect precisely while labelling it gently is not partial credit — it is the whole failure, because the label is what determines whether anyone looks again.
4. Nothing is implemented until its spec is marked Approved. Check the Status line first.
   - **Approval is a review by the repository owner, not a state field.** The Status line records an approval that already happened; it is not what makes one happen. **The author of a spec may never move it out of Draft** — an implementer who sets the field is satisfying the gate by writing the thing the gate reads, which passes the check for a reason unrelated to what it protects. Only the owner moves a spec to Approved, and the commit that does so is theirs.
   - **An instruction to implement is not an approval.** "Then implement SPEC-NNN", "start on it", "do that next", a deadline, a priority, or any other scheduling statement says *when* to do the work, not that the decisions in it have been reviewed. A review reads the Key decisions and the Acceptance criteria and responds to them; nothing shorter is one. Treating the two as interchangeable is how an unreviewed design ships with a green check beside it.
   - **Amending an approved spec needs approval too, and where it comes from depends on who raised it.** Rule 4 covered Draft→Approved and said nothing about the far more common case, which is changing a decision in a spec that is already Approved and implemented. Two kinds, and they are not close:
     - **An amendment the owner asked for is approved by the asking.** The request *is* the review — it read the decision, chose between options, and said what to do. Apply it in the same commit as the code, mark it as an amendment with its date and its origin, and say in the commit that you read it as approval so the owner can push back cheaply. **SPEC-006 Key decision 16, amendment 5 (2026-08-01) is the worked example**: the owner's message named the flaw, chose which of the two overshoot sources to fix, specified the mechanism, rejected an alternative (a second semaphore), and dictated the client-facing rendering. That is a review, and asking for it to be repeated as a Draft would be ceremony.
     - **An amendment you propose unprompted stops at proposed.** Write it, argue it, and mark it **Proposed** in the spec with what it would change and what breaks without it — then stop. Do not implement it, and do not fold it into an approved amendment's commit where its approval would be inherited from something adjacent to it. The failure this prevents is the quiet one: a decision that nobody chose, shipped alongside one they did, indistinguishable afterwards.
   - **The completion clause: a ratification that has not moved the Status line has not happened.** *(added 2026-08-05, after SPEC-007 spent eleven commits Approved-in-conversation and Draft-in-file.)* Everything above puts the Status move with the owner and **required nothing of the owner**, so an item-by-item review could be given, recorded inside the spec as amendments, implemented against — and the artifact would still say nobody had reviewed it. **The review is the substance and the Status line is the record; a decision with no canonical home is not yet a decision anyone can act on later.** The asymmetry that made this invisible is worth naming: the implementer cannot fix it (rule 4 forbids it) and the owner has no prompt to, because everything downstream keeps working.
   - **So it is enforced rather than remembered, like everything else here.** `tests/test_spec_hygiene.py` fails the build when a spec whose acceptance criteria are cited by the test suite still reads `Draft`. Citing an AC in a test *is* the claim that it is implemented, which makes it the honest trigger: it fires exactly when rule 4's "nothing is implemented until its spec is marked Approved" has already been violated, and it cannot be satisfied by anything except an owner moving the line.
   - **If you believe you have approval implicitly, say so and stop.** Name the spec, name what you think granted the approval, and ask for it explicitly. Do not implement, and do not set the Status line while waiting. Being blocked for one exchange is cheap; an unreviewed spec discovered after implementation is not, because the cost of changing a decision then is the code, the tests, and the review that already happened.
5. Spec + tests + code are committed together; when implementation forces a decision change, the spec is updated **in the same commit**.
6. Every implementation commit references its spec.
7. **Every claim a spec makes about the system is swept against the system — and a *guarantee* needs either a test or a stated bound.**
   - **The criterion is a claim about the system, not a claim about code.** The sweep after the third review round checked claims about code that exists — "records go to stdout" (they go to stderr), "~90 lines" (it was ~150) — and that criterion was too narrow to catch anything else. SPEC-006 KD-16's "the overshoot is bounded and computable rather than hoped for: at most `spend_rate × TTL × replicas`" **survived that sweep**, because it is a claim about an emergent property and **no single line of code contradicts it**. It was false: it described cross-replica staleness and silently omitted concurrent in-flight requests on one replica, and it was "computable" only under a bounded arrival rate that KD-14 explicitly leaves unbounded. Sweep for anything asserting what the system does, is, cannot do, or costs — every "at most", "bounded", "never", "always", "cannot", "guaranteed", and every formula.
   - **A guarantee needs a test that fails when it is broken, or a stated bound naming what it does not cover.** Preferably both. This is rule 3 pointed at prose instead of at assertions: an untested guarantee is true for whatever reason its author had in mind, which is exactly the thing rule 3 says only a failing run can distinguish. A formula in a spec is an assertion with no test runner attached, and it decays the same way — silently, and in the direction that flatters the design.
   - **Where the guarantee has a term nobody can bound, say so and name it.** "Bounded by `ceiling + one worst-case query`, and separately by `(N−1) × TTL × arrival rate × per-query cost`, which is zero at one replica and deferred to SPEC-010" is a guarantee. "Bounded and computable rather than hoped for" was a hope written in the indicative.
   - **Second instance, found one day after this rule was written** *(2026-08-02)*: SPEC-006 KD-14 accepted no rate limiting partly "because keys are not public". That is a guarantee about the system, it has no test, and it goes false the moment a browser holds the read key — which is what SPEC-009 does by existing. The claim was true when written and true of every client the repo has today; what was missing was the boundary. Corrected to name the class of client it holds for, with the exposure recorded and the mechanism handed to SPEC-010. **A guarantee that is true of today's clients and silently false of tomorrow's needs its scope written into it**, because the sentence outlives the assumption that made it true.
   - **Third instance, and the gap it exposes: sweep a Draft before submitting it, not only an approved spec** *(2026-08-02)*. SPEC-007's first draft claimed "SPEC-006's ceiling does not apply — this runs offline against the libraries, not through the API." False, and by one line: `Generator._write_query_log` writes the `query_log` row, `SpendGuard` sums every row in the window, and the ceiling is not an API-layer feature that offline code escapes. It was caught by the owner asking rather than by any sweep, because the two triggers below — an amendment, or changed code — cover neither *"a spec I am about to hand over"* nor *"a claim about a **different** spec's mechanism"*. Both are now in scope. **The tell to look for: a sentence asserting that some rule does not apply to you.** That is a claim about someone else's mechanism, and it is the one kind a spec author is least positioned to check.
   - Sweep when a spec is amended, when code the spec describes changes, and **before handing over any Draft** — including its claims about mechanisms other specs own.
   - **The reviewer-side twin: a wrong threshold with a reason attached survives review better than one without.** Everything above tells an author to check their claims. This one is about what happens at the gate, and it is the reason a swept spec can still ship a false claim: **a justification does not merely fail to help, it actively lowers the guard**, because reading a reason produces the feeling of having checked one.
     - **Fourth instance, and the first one the reviewer caught in themselves** *(2026-08-02)*: SPEC-007 KD-12's `discordant_pairs >= 25` arrived with a worked example — an 18–7 split gives p = 0.0433 two-sided — and a general claim: "below 25, no split the set can produce reaches α = 0.05." The reviewer checked the **example**, found its arithmetic correct, and approved the **claim**. The claim was false by a wide margin: **6–0 gives p = 0.031**, and the smallest n at which any split can reject is 6, not 25. The threshold was also unreachable, since discordant pairs are bounded by a question count of 26. It survived a review *because* it came with a reason.
     - **The mechanism, stated so it is recognisable next time: the example is chosen by the author and therefore sits where the claim is true.** The boundary is where it fails. "Below 25, nothing reaches α" is a claim about n = 6…24, and it was tested at n = 25 — the one value it does not cover. Checking an author's illustration is not checking their generalisation; it is confirming the case they already confirmed.
     - **What to do instead: evaluate the claim at its boundary, not at its example, and prefer the cheapest adversarial value over the author's demonstration.** For a threshold, that means the smallest and largest values it admits. For a bound, the term the author did not vary. For "no X can Y", one X. **A number offered with a reason should get *more* scrutiny than a bare one**, because a bare number announces that it is unjustified and a justified one conceals it.
     - This is rule 3 aimed at prose review rather than at tests: an assertion that passes is indistinguishable from one that cannot fail, and an argument that convinces is indistinguishable from one that was never tested against the case that breaks it.
8. **When work is blocked behind an expensive or slow step, find the cheapest experiment that could falsify that step's premise, and run it first.**
   - Not "consider cheaper alternatives", which is advice nobody can be held to. The rule is mechanical: **before starting the expensive step, write down the premise it rests on, then ask what the cheapest thing is that could show that premise false.** If that experiment costs materially less, it runs first, and its outcome decides whether the expensive step happens at all.
   - **It applies to work that is already approved.** Approval says the design was reviewed; it is not evidence that the premise is true, and the cheap falsifier is cheapest precisely when it runs before anyone has invested.
   - **Worked example, with both costs** *(2026-08-02)*. The corpus ladder. **Premise:** `recall@8` is pinned at 1.000 because the corpus is too small and not confusable enough. **The expensive step:** a three-rung ladder of seven documents — a spec amendment, a registry, resumable fetch, per-document size guards, pre-flight probes, an owner approval gate at every rung, a scratch-database competition probe, and **$0.0176** of embedding for the probe alone — spread across **three rounds of review** and blocked on approval throughout. **The cheapest falsifier:** rewrite fourteen questions and re-measure the *unchanged* corpus. **$0.00002 and one afternoon.** It falsified the premise outright — `recall@8` fell from 1.000 to 0.714 with nothing fetched — and it was available from the first round. Roughly a thousandfold cost difference, and it ran third.
   - **The tell, which is what makes this checkable rather than obvious in hindsight: the premise named a variable that is hard to change and held fixed one that is easy to change.** The ladder proposed moving the corpus while freezing the questions. **When a design freezes the cheap variable and proposes to move the expensive one, that ordering is worth a paragraph of scrutiny before it is worth a spec amendment** — and the paragraph is: what would we see if the cheap variable were the cause?
   - Rule 7's reviewer-side twin asks whether a claim was checked. **This one asks whether the cheapest check was run first.** Both failures feel like diligence while they are happening.
9. **A pre-specified failure mode bound to the primary metric can miss the failure entirely, because the primary metric may be insensitive to it. Name the mechanism, then enumerate the metrics it could appear in — or state explicitly that the falsifier is metric-independent.**
   - Pre-specifying how a change might fail is right, and rule 8's cheap-experiment discipline depends on it. **The trap is binding the prediction to the number you happen to be watching.** A mechanism does not know which metric is primary; it surfaces wherever it surfaces.
   - **Worked example** *(2026-08-02)*. Before applying SPEC-004's OR fallback, the failure mode was written down and the mechanism was named **correctly**: *fallback candidates displacing good vector results in fusion*. The falsifier attached to it was *"a question where hybrid's `recall@8` is worse than vector-only's"* — bound to `recall@8`, the pre-registered primary metric. **`recall@8` improved.** The failure appeared one rank-level up: `recall@1` on citation queries fell 0.929 → 0.714, with 8 of 13 top-1 misses traced to exactly the predicted mechanism. **The prediction was right and the falsifier could not see it.**
   - **The fix is mechanical.** Having named a mechanism, ask: *at which observation points would this be visible?* For a ranking change: recall at every k that is reported, MRR, the identity of the top-1, the discordant cells, latency. Then either enumerate them in the falsifier, or write **"metric-independent: any degradation traceable to <mechanism>, at any k"** and mean it. A one-metric falsifier is a claim that the mechanism can only manifest there, and that claim is almost never true and almost never stated.
   - This is rule 3 pointed at predictions rather than at assertions: a falsifier that cannot fire is indistinguishable from a mechanism that did not occur, and only the mechanism-level check separates them.

> **MEASURED AND CONTRADICTED — 2026-08-05, commit `2e81ec0` (result) and this commit (deletion).** This note began on 2026-08-02 as *scoped and unverified*: "full-text search nails them" was the load-bearing claim under the second branch, the RRF fusion step, the `tsvector` column and SPEC-004's two-connection design, and it had **no test and no stated bound**. It has now been answered.
>
> **SPEC-007 KD-12's confirmatory comparison, 120 questions, pre-registered:** hybrid against dense-only, `recall@8` at k = 8. **b = 3, c = 20, p = 0.000488** two-sided exact. Vector-only wins. All twenty of the discordant cases carrying the result were human-verified with zero corrections.
>
> **The finding underneath the finding is the conjunction, not the fusion.** `websearch_to_tsquery` was satisfiable on **19 of 120** questions; on the other 101 the AND emptied and the OR fallback fired, including on every one of the 23 discordant pairs. On the 19 where the conjunction did fire, the branch reordered inside the top 8 and **never changed whether the gold was found**. Gated it contributes nothing; ungated it costs 20 and returns 3.
>
> **What is refuted is this implementation** — AND conjunction with OR fallback, RRF at k = 60, on this corpus and this question mix. **It is not a finding that lexical retrieval cannot help**, and pilot-2 is the record pointing the other way: on fourteen deliberately lexically-anchored questions, hybrid scored `recall@8` 1.000 against vector-only's 0.857 (b = 2, c = 0), too small to be conclusive and narrowed further by the fact that 7 of 18 citation-anchored questions also emptied their conjunction. A different design — per-term weighting, score-based rather than rank-based fusion, a query parser that handles out-of-vocabulary terms — is **untested, and untested is not refuted**.
>
> **We cannot test it, and the reason is procedural rather than technical:** the confirmatory set is unblinded and permanently closed (SPEC-007 KD-12 amendment 8), so nothing designed after 2026-08-05 can be validated against it to the standard this result was produced under. **A second authoring cycle is the price of asking again.**
>
> The branch, the fallback, the fusion step, the `tsvector` column and the unreachable HNSW index were removed under SPEC-004 Key decision 15. **The architecture claim that survives is the one about the datastore, not the one about the branch:** one Postgres provides exact vector search and the relational layer for query logs and eval runs, which is still one Flexible Server instead of two services.
